# Changelog

What changed in Immunity Core that a person who runs it, their agent or a program built on its commands would notice. Everything else is in the Git history.

Immunity Core has no numbered release yet. Entries go by the day a change reached `main`, newest first, and each day names the commit `main` ended on, so a program that pins the core by commit can find its place. Two numbers move on their own: the version of the contract, which is the version of the crate `immunity-contract`, and the format of the store. A build refuses a store of another format and says how to start over.

### Changed

- The store has format 11, and a store of format 10 is refused: the store starts over, with the answers to findings, the statements about machines, the verdicts and the journal of the old one left in the old file. See [updating and removing](docs/reference.md#updating-and-removing). Beside the coverage of a full reading of a project's lockfiles, the store keeps each file the reading opened, with its SHA-256 and the build that read it (`coverage_file`). Every match of every rule is kept in the record by the place of its line, with the finding it went to, and goes with its log file; a log file is told from another of the same name by the SHA-256 of its first 64 bytes, never by the bytes themselves, and a row of the record keeps a hash of its line; the counts of the event level are a row for each ten seconds and running totals that only grow. A log file that leaves, is replaced or is cut short before it was known read to its end counts as deleted unread, and the notes of the tidy job are counted after the last one counted, never by their time. A full check that cannot read a file of the log concludes that the event level's reading failed, with the lines before that file written. Format 11 is still being made: a store that a build from `main` made in format 11 is started over by hand when `main` changes the store's shape again.
- A full check does not parse a project's lockfiles again while nothing they hold can have changed: every file its last full reading opened has the same SHA-256, no lockfile appeared or went, the build is the same, and the facts that reading found are still live. Its reading is then written again as this check's, full, so the store and every answer are what a full reading of the same bytes leaves. A project with a lockfile that cannot be read now, a folder that cannot be listed, or a last reading that was not full is read as before, and so is a project that left and came back. The check holds the store for less time, so an event recorded during it waits less.
- The band at the top of the summary `immunity view` writes keeps a line for each fault about Immunity Core's own work: a check that did not finish, the watcher and its failures, an answer that is not fresh. Every other fault `immunity status` lists is a reading or a download that failed. The band counts the things they are about on one line, with how many the person can fix, and links to a new section of the summary, "Could not be read". That section tells each one in full, the ones the person can fix first and marked, and it replaces "You can fix" and the section of the page of this Mac that named the rest. "What is watched" is now "What is read". Kinds of place that hold nothing and were read in full are folded into one line under their group. The page of this Mac opens with the same rows for this Mac and its projects. An opened row of findings no longer repeats what a source said when its evidence already gives it, as a vulnerable package's records do. `store.view_sections` names `not-read` and `not-read-here` in place of `you-can-fix` and `limits`.
- The summary `immunity view` writes draws the findings of one rule about one thing in one row: a package with the same releases in several projects, as a folder of git hooks already was, with in how many projects or files it is.
